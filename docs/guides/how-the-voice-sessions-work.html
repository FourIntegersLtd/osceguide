How the voice sessions work

When someone talks to a simulated patient, a tutor or the help assistant, a small program on a server listens, thinks and answers out loud. This page follows each kind of session step by step, in plain words, and says what you would see if a step fails.

The cast, in one minute

Think of a voice session as a private phone call that an AI joins. Five parties take part, and every diagram below uses the same five.

The browser

The learner's page. It holds the microphone and the speakers. It never talks to an AI model directly.

platform-api (the backend)

The one server that knows who the learner is, which station they are on, and what the patient should say. It writes the patient's instructions and, afterwards, marks the transcript.

LiveKit (the room)

A service that carries live audio. A room is a private call; people and programs join it with a one-use pass called a token.

The worker

Our program that joins the room as the patient (or tutor, or helper). It does not decide what to say: it asks the backend, then listens and speaks.

AI models

Three jobs: speech-to-text (ears), a language model (brain), text-to-speech (voice).

The one rule that shapes everything

The worker never marks anything. It delivers a transcript back and stops. Scoring happens later, on the backend. If a mark looks wrong, the transcript is the first thing to check, not the voice.

Session 1

A practice consultation: the simulated patient

A learner starts a station and talks to an AI patient. Nobody else is in the room.

Step by step

  1. Start. The learner opens a station. The backend creates an attempt (one recorded try at a station). Without a seeded exam and a published rubric the backend refuses with an "unknown exam" error, which looks like a worker fault but is not.
  2. Ask to join. The browser asks the backend for a pass to the room. The backend only answers for the attempt's owner, and only if the attempt is not finished.
  3. Pass and dispatch. The backend issues a token for a room named after the attempt, and attaches a dispatch to it: a note telling LiveKit "send a patient worker to this room". The note carries only three strings: attempt id, which backend, and the candidate's reference. Everything else is fetched later, so the note cannot drift out of date.
  4. A worker picks it up. LiveKit offers the job to a worker whose name matches. The name is fixed for each environment, which is why a laptop must use its own (section 5).
  5. Fetch the script. The worker asks the backend for the attempt, proving who it is with a shared secret. The reply holds the patient's fully written instructions and the scenario. The worker refuses to start if the instructions are blank, and it never sees how the transcript will be marked.
  6. Learner joins. The browser checks the microphone, joins the room and waits. The worker waits up to 120 seconds for the candidate; after that it leaves quietly. If two workers arrive for one room (a duplicate dispatch), the one that sorts first stays and the other leaves.
  7. Speech in. The learner speaks. Deepgram (nova-3-medical) turns the audio into text.
  8. Brain and voice. A language model writes the patient's next line, in role, and a text-to-speech voice says it. Greetings come from a fixed greeting, not the model.
  9. Speech out. The patient's audio travels back through the room to the learner.
  10. Transcript back. As the talk goes on, the worker sends each message back to the backend. When the learner leaves, the room closes or the worker is removed, it sends the whole transcript once more. A non-success reply counts as a failed delivery.
  11. Marking, backend side. The completed transcript queues a marking job. A separate engine reads it against the rubric and stores the result. This is the part another team owns; the worker is already gone.

What can go wrong, and what you would see

  • Learner presses start and sees a "waiting in line" screen. Every seat is taken. The token route answers 202 with a place in line, and the page counts down until a seat frees up. This is normal under load, not a fault.
  • Room joins but nobody ever speaks. The worker could not fetch the script (wrong secret, attempt missing or no rendered instructions) and returned without a word. The room looks fine and the patient never arrives. Check the worker logs for "bootstrap failed".
  • Two patient voices at once. A duplicate dispatch. The worker tie-break removes one, but a token that attached a dispatch where the circuit also dispatches caused this in the past.
  • A finished consultation never gets a mark. Usually the station has no patient information, so it rendered degraded and is silently never marked. Check the stored result, not the screen.
  • Patient voice sounds like the tutor, or breaks role. Voice and model are settings, not code (section 5). A model swap should be re-measured before it ships.
Session 2

The debrief with the tutor

After a consultation the learner can talk it through with an AI tutor for about ten minutes.

A debrief is a second kind of attempt, tied to the consultation it discusses. It runs on the same assessment worker as the patient, but with a different script and a different (stronger) model. It needs a recorded consultation: with none, the backend refuses to start it.

PEARLS, not a checklist

PEARLS is a way of giving feedback as a conversation: partnership, emotion, restatement, support, hypothetical questions, summary. The tutor starts with how it felt, then walks the management plan together, using Advocacy-Inquiry to raise gaps. It is not Pendleton (strengths first, then improvements); the code says so on purpose.

The ten-minute clock

A language model has no sense of time and tends to wrap up too early. So the backend writes a timing plan and the worker pushes timed notes to the tutor: about 2:30 "you should be into the plan", 5:00 "half has gone", 8:00 "two minutes left, start closing", 10:00 "finish warmly". The tutor can also silently check the clock itself. The clock never ends the session by itself.

Playing the patient, once

The tutor is locked into its role, with one written exception: it may play the patient a single time so the learner can try a moment again. Separately, the debrief chooser offers "Practice as the patient", where the help worker plays the doctor and the learner plays the patient. That one needs a finished attempt and is switched on per exam.

Summaries are kept

After the debrief the backend writes one summary per attempt (the table refuses a second). It feeds the tutor's memory of the learner and shows in the learner's debrief history, which lists more than the 20 the tutor itself reads.

  1. Choose. The learner picks a finished consultation and starts a debrief. The backend checks it is theirs and has a transcript.
  2. Plan. The backend renders the tutor's instructions and the pacing plan from the same numbers, so the prompt and the clock cannot disagree.
  3. Token and dispatch. As in session 1, with the debrief kind selected.
  4. Join and fetch. The worker fetches instructions plus the pacing plan.
  5. Speak. The tutor model (gpt-5.4-mini) and the tutor voice carry the conversation.
  6. Clock. The worker injects the timed notes between turns, never mid-sentence.
  7. Hand back. The debrief transcript is posted and a job writes the summary in the same sitting of work.

What can go wrong, and what you would see

  • The tutor rushes to goodbye after six exchanges. The clock plan did not arrive, so the tutor is pacing by turn count. Check that the timing plan and the clock check were in what the backend sent the worker.
  • "Debrief needs a recorded consultation". The source attempt has no saved transcript chunks, so there is nothing to discuss.
  • A returning learner is greeted as new. "Returning" is decided only by a stored session summary note. A session in which the learner never spoke writes none.
  • Summary missing from the history. The summary is made by a background job after the call; it can lag, and a failed job leaves a gap rather than a wrong entry.
Session 3

Help: the assistant worker

A friendly voice (Athena) that explains the product and can point at the screen. Nobody is assessed.

This is the second worker, a separate program from the patient. It handles four kinds of session, each a row in one table in the code: help, onboarding (a guided walk through the app), dashboard (narrating the learner's progress) and consulting-doctor (Athena plays the doctor so the learner can practise being the patient).

What it can do

  • Answer from a help guide that is rendered into its instructions in full (there is no search tool for it).
  • Look at the learner's screen when asked, through a screenshot taken in their browser, and point with an on-screen pointer.
  • Scroll and click on the learner's behalf, with a time limit on each action and a rate limit per minute.
  • Ask the backend questions through "remote tools", used for the dashboard narration.
  • For voice-only FAQ help, run speech-to-speech instead of the ears-brain-voice chain.

What it cannot do

  • Score, mark or change any attempt. It has no access to the marking engine.
  • Know product names, menu labels or exam ids. It only knows what the backend wrote into its instructions.
  • Keep every conversation. Help is kept as a record, a dashboard session is summarised and then deleted, and onboarding and consulting-doctor are thrown away unread.
  • Run for ever. A one-hour wall-clock cap shuts any session, and screen capture is read-only.

What can go wrong, and what you would see

  • "I could not find that" for an answer that should exist. The help library has no relevance threshold, so the usual cause is an out-of-date index of help material. A platform admin can rebuild it.
  • Athena cannot be opened from the page. The open-Athena event is heard by a lazy wrapper until the dock loads, then by the dock. Both must stay in place.
  • The pointer lands in the wrong place. The pointer is a hidden instruction in the reply, cut out before it is spoken. If the screenshot and the page differ in size, the coordinates drift.
  • The voice stops after about an hour. The session cap, by design.
Session 4

Group sessions: exam circuits and peer practice

Two different things share a room idea. Only one of them involves an AI.

4a. Exam-day circuits

In an exam, a circuit is a timetable of stations. The server owns the clock (a decision recorded as ADR 0018): the browser shows a countdown but never decides when a phase ends. Candidates and examiners join the circuit's room during the reading phase (3 minutes by default). The candidate's token carries no worker. When reading ends, the circuit itself dispatches the patient.

  1. Start. A supervisor starts the circuit; from here it runs itself, with controls to pause, extend or send the patient in by hand if something goes wrong.
  2. Join early. The candidate takes a token with no patient attached. If the token carried one, a second patient would arrive beside the circuit's own.
  3. Examiner. An examiner's token cannot publish audio or data at all. This is a guarantee, so a candidate cannot be prompted and the transcript stays a pure record.
  4. Reading. The server counts down the reading minutes. The candidate reads their brief.
  5. Patient in. The server creates a fresh attempt and dispatches the patient. A re-dispatch fails the old attempt rather than overwriting it, so the first recording is kept.
  6. Consultation. 10 minutes by default. The worker has no timer of its own.
  7. Bell. Removing the patient from the room ends the consultation. On its way out the worker posts the full transcript, which queues marking: "the bell goes" and "the recording is delivered" are the same act.

What can go wrong, and what you would see

  • Reading ends and nobody speaks. If nobody joined the room during reading, the circuit sits overdue for ever. If someone did, a patient dispatched more than 60 seconds ago with no recording gets one automatic resend per station; the supervisor can also press resend.
  • A trainee was removed after the circuit was built. Their slot gets no recording, so nothing is marked for them.
  • A second patient voice. A stale agent from a previous dispatch; the backend clears them first with a short settle pause.

4b. Peer practice between two learners

Yes, it uses LiveKit, but there is no AI worker. Two real people are paired, one as the doctor and one as the patient, and talk in an ordinary room. The backend hands each a token with no dispatch. Its phase clock (preparation 3 min, consultation 12 min, debrief 15 min by default, adjustable per exam) lives on the server. Each side has 2 minutes to accept a pairing, and a waiting learner is re-queued after up to 10 minutes.

The consultation is recorded by LiveKit's egress (a built-in recorder) into storage. When the phase ends a background job waits for the file, transcribes it and separates the two voices (a diariser), then produces feedback. A recording is best effort: if it fails, the consultation still counts.

What can go wrong, and what you would see

  • The session says "not yet accepted". One side has not accepted the pairing. There is no way into the room until both have.
  • Feedback never appears. The transcription job gives up after twenty looks if the recording never lands in storage and records why on the session.
  • A stranger cannot open a session link. Deliberate: the answer is "not found", so nobody can confirm a session exists.

What does not exist

There is no AI participant in peer practice, and no group room where several candidates face one patient at the same time. A circuit has one candidate per station sitting; others wait their turn. The old voice programs are not described here because they are switched off.

Section 5

Under the hood

One worker per process

The same image can run either worker. An environment variable (OSCE_LIVEKIT_WORKER) picks assessment or assistant, and the program refuses to start on any other value. No shell or supervisor sits in front of it, so the stop signal reaches LiveKit directly. Otherwise a pod being shut down would keep accepting sessions.

Capacity and seats

Each pod caps its live sessions. The shared default is 6 patient and 3 assistant sessions per pod, with 3 pods of each in production. Staging runs one pod of each, capped lower (2 and 1) because it shares machines with production. Beyond the seats, learners wait in line; a circuit never waits but does take a seat.

Draining

On shutdown a worker keeps finishing live sessions for up to 840 seconds, inside the pod's 900-second grace period.

Cloud or ours

The backend can send a session to LiveKit Cloud or to our own workers. Cloud overflows to ours when full; ours never spills onto Cloud, because that would be an unplanned bill.

Staging, production and your laptop

Workers run on a small cluster in two namespaces (separate rooms of the same building): assessment-platform-staging and assessment-platform (production). A push to main that touches assessment/ deploys staging; production only happens when someone presses "Promote workers to production". Settings that differ live in the staging and production overlays, never in the shared base.

Why a local worker needs its own names

Workers are found by name. Staging's are called assessment-self-hosted and assistant-self-hosted. If a worker on your laptop uses those names it joins the same pool and steals staging's sessions: a tester hears a patient with your half-finished code. Set LIVEKIT_AGENT_NAMESPACE=dev-<you> and name your workers dev-<you>-assessment-self-hosted and dev-<you>-assistant-self-hosted. The backend adds the same prefix when it dispatches.

Speech settings and models

No model is written into the logic. They are defaults in one settings class, each overridable by an environment variable named VOICE_<FIELD> (for example VOICE_PATIENT_LLM). Defaults at this commit:

A typical session, to scale

The bars use real defaults from the code: a generic 12-minute consultation clock, a 10-minute debrief, and the circuit and peer-practice defaults. A real station supplies its own timings from its rubric, so treat the solo row as the fallback.

Other timers worth knowing

  • Greeting: 10 seconds to say the opening line.
  • Patient worker waits 120 seconds for the candidate; the assistant waits 30.
  • Assistant session hard cap: 3600 seconds.
  • When a learner ends, the room is closed at once so the seat frees now, rather than after LiveKit's own empty-room timeout of about 20 seconds.
