This page is load-bearing. Keep it current.

The backend is still being rebuilt. Every slice that lands, every column added or dropped, every constraint tightened changes what is true here — and a schema reference that is 80% right is worse than none, because people stop checking it against the code and start trusting it.

The rule: a migration and this reference change in the same commit. The rule CONTRIBUTING.md already applies to tests — no behaviour change without a test beside it — applies to the schema too. If make new-migration produced a diff, this is part of that diff. A pull request that adds a table and not its entry here is incomplete in the same way a pull request with no test is incomplete.

It is no longer a promise. api/scripts/check_data_model.py imports Base.metadata, diffs table and column names against the rows below, and fails on anything in one and not the other. It runs in make arch, so it runs in make ci; make data-model runs it alone, and also fails when this page's generated schema block or route list has drifted (api/scripts/build_field_guide.py). It is tolerant about form and strict about presence — a field row, a pair on one row, a sentence for a join table and the published_at/by shorthand all satisfy it, and a column mentioned nowhere does not. It cannot check the half that rots silently: whether the reason given for a delete rule is still the real one.

What must stay true, not merely present. Column names and types are the easy half, and the half a checker can hold. The half that rots silently is the reasoning — why a delete rule is RESTRICT, why a unique index is partial, why a column is JSON. When a constraint changes, change the sentence explaining it, or the next engineer implements against a rationale that no longer holds.

The repository copy lives at api/docs/DATA-MODEL.md. The schema section below is generated from it and from Base.metadata by api/scripts/build_field_guide.py (run PYTHONPATH=. poetry run python scripts/build_field_guide.py from api/ after a migration); the route list is checked against api/openapi.json by the same script.

Part one · start here

The words this codebase uses

Read this before the schema. Most of these terms come from UK postgraduate medical examining rather than from software, they are used precisely, and several look like synonyms while naming different things — a cohort is not a trainee group, a slot is not an attempt, and an entitlement is not a payment.

Part two

One attempt, traced end to end

The single flow that crosses every boundary in the system: browser, API, the marking engine, LiveKit, the voice worker and the job queue. Follow this once and the rest of the codebase has a shape. Each step names what it writes, and the notes are the reasons a step exists in the form it does — most of them are a legacy failure that is not being repeated.

Phase 1The candidate startsbrowser → platform-api
01platform-api POST /api/v1/attempts → attempts.service.start_attempt Resolves the exam code to a row, then applies the entitlement gate. The gate lives here, not in each caller, so every route that can start a session — practice, a set entry, a slot dispatch, a peer session — passes through the same check, with free-trial state resolved alongside it. writes: attempts · status = created · no definition yet
02platform-api POST /api/v1/attempts/{id}/voice-token → voice.service.grant_for_attempt Refuses an attempt that is not yours, or one already at interaction_complete, evaluated or failed. Maps the attempt kind to a session type and then to a worker family — with no default, deliberately: defaulting here would undo the guarantee that a patient simulation is never dispatched to the help worker. If the configured mode is Cloud, capacity is checked by slots_free, which reserves the slot as it answers, because asking and then taking would race; past the cap it falls back to our own workers rather than refusing. The token carries exactly three metadata strings, which is what stops the dispatch payload becoming a second, drifting copy of the attempt. writes: a Redis cloud-slot reservation, when routing Cloud
Phase 2The worker joinsLiveKit → worker → platform-api
03voice worker Joins the room and reads the backend label from the token metadata It looks this API up by that label in its own VOICE_BACKENDS_JSON, which is how platform-api, b2b-api and b2c-api can all be live at once under different labels during the cutover.
04voice worker GET /api/worker/attempts/{id} with X-Worker-Secret → bootstrap On the first bootstrap the definition is rendered here: the runnable station version and exam are loaded and handed to the engine's renderer. It is frozen only if the render was real. A degraded render — a station whose scenario will not render — is still served so the session is never blocked, but not persisted, so the next bootstrap tries again and the attempt gets the real thing once the station is fixed. Both legacy backends freeze unconditionally, which is why an unresolved station there pins a generic patient prompt to the attempt forever, and every replay shows the same. The response is two objects, and the worker validates both against the engine's own models: the attempt, and a scenario carrying the case identity, its title and the patient's gender — which is what the worker picks the voice from. Both models forbid unknown keys, so a scenario of roughly the right shape is not good enough: an earlier one carried ref, title and raw, which the engine rejected on three counts, and no live session could start at all. A contract test now parses a real bootstrap with the engine's own classes rather than checking that the keys are present. writes: attempts.definition + definition_frozen_at, on a real render only
05platform-api The same call moves the attempt created → running A worker fetching the bootstrap is the session beginning — it is the only start signal that exists, since nothing else reports one. Without it the attempt stays created, the finished transcript cannot move it to interaction_complete, and the marking is never queued: an unmarked attempt with a full transcript sitting behind it. writes: attempts.status, started_at
Phase 3The conversationworker → platform-api, repeatedly
06voice worker POST /api/worker/attempts/{id}/transcript-chunks, turn by turn Best-effort: the worker never reads the response, so posts repeat. Deduplicated on (attempt_id, message_id) rather than trusted to arrive once. writes: transcript_messages
Phase 4The session endsworker → platform-api → job queue
07voice worker POST /api/worker/attempts/{id}/transcript → accept_transcript The final transcript is the authority. Chunks are best-effort and may have been dropped, so anything missing is filled in from this payload rather than assumed to have arrived. writes: transcripts.complete · attempts.status = interaction_complete
08platform-api enqueue_scoring, inside the same transaction Deliberately not procrastinate's defer_async: its connector holds its own pool, so deferring through it commits the job on a different connection and the job could land while the transcript that justified it rolls back. Calling procrastinate's SQL function on our own session keeps it to one transaction — the work and the fact that it is owed are recorded together, so either both land or neither. The queueing lock score:{attempt}:{policy} makes a redelivered transcript idempotent. writes: a procrastinate job row, in the request transaction
Phase 5Markingjob worker → the engine
09job worker score_attempt picks the policy off the frozen definition So re-marking a past attempt uses the framework it was actually run against, rather than whatever the station says today. If there is no frozen definition — a transcript arrived for an attempt the worker never bootstrapped — it falls back to the exam's own framework with a warning, because the alternative was a log line and a transcript nobody would ever score, which is what happened.
10job worker Three guards before the engine is called Already scored under this policy → nothing written, because the queue may deliver twice. Status not markable → skip, since a job can arrive before the status settles or after a later failure. Empty transcript → the attempt is failed with reason empty_transcript. And if the evaluator itself raises, the attempt is left at interaction_complete so a retry can still mark it — failing it there would discard a transcript we still hold.
11job worker The engine's payload is stored and the attempt moves to evaluated Unique on (attempt_id, policy_version), so a second run under the same policy writes nothing and a run under a different one sits beside the first rather than replacing it. Re-marking never moves an already-evaluated attempt's status. writes: assessment_results · attempts.status = evaluated
Phase 6Reading it backbrowser → platform-api
12platform-api GET /api/v1/attempts/{id}/result and /transcript Visible to the attempt's owner and to platform admins. An institution's formal decision is a different path entirely — candidate_result_revisions, signed off and released — and a candidate sees that only through GET /me/results/{sitting_id}, only once released.
VariantWhen it is an examinationthe exam_slot path · ADR 0018
→platform-api The circuit's own clock replaces steps 1–2. Nobody presses anything. The candidate joins the circuit's room once, at the start, with POST /me/circuits/{id}/join-token — a token carrying no agent dispatch, because the orchestrator brings the patient rather than their token carrying one. Attaching one here put a second patient in beside the first, and both answered as the patient. When the reading period's deadline passes, the transition scheduled for that moment fires: the attempt is created and the agent dispatched into the room, in one transaction. Each dispatch creates a new attempt — which is what the partial unique index enforces: a slot may have at most one attempt that has not failed, so sending the patient again fails the previous one rather than overwriting its recording. writes: attempts · circuits.phase = simulation · the next transition, scheduled
→job worker The consultation's deadline passes and the agent is removed That is how the recording ends. The worker has no timer of its own — it ends on the candidate leaving, the room closing, or being removed — and on its way out it posts the full transcript, which queues the marking. So the bell ringing and the recording being delivered are the same act, and phases 3 to 5 follow unchanged. Two overrides create a second attempt: resend-patient, when the patient did not arrive, and redo-station, when the station has to be given back. Both fail the live attempt rather than deleting it, so what happened the first time survives beside the retry.
→job worker sweep_circuits, every minute The safety net, not the mechanism — if it were the mechanism every transition would be up to a minute late. It covers what a scheduled job cannot: a worker that was down when a phase ended, a transition that rolled back, a deploy mid-examination. It is also the twelve-hour reaper for circuits nobody closed. A scheduled job is found by polling rather than by notification, which is why WORKER_FETCH_JOB_POLLING_SECONDS defaults to 1.0 here and not procrastinate's 5.0.
Part three

The data model

Each slice owns its tables and no other slice imports them. Unless a row below says otherwise, every table carries id uuid primary key and created_at / updated_at from the shared mixins; citext is used wherever a human types something and expects it to match case-insensitively.

Part four

The API, by who calls it

Everything public sits under /api/v1. The voice workers use /api/worker with a shared secret, and /health sits outside both. The badge on each route is the FastAPI dependency that actually guards it.

Part five

The system map

Which repository owns what, and what talks to what. This is the part that is currently tribal knowledge, and the part most likely to send a new engineer to edit the wrong checkout — two of the directories below are frozen and one of them looks perfectly alive.

Repositories in this workspace

One repository, FourIntegersLtd/osceguide, with one folder per app: api/, web/ and assessment/. Each deploys on its own, only when its own folder changes. The legacy backends live in the old backend repository and are retiring.

api/This backend (platform-api). FastAPI, SQLAlchemy, Alembic, procrastinate. Replaces both legacy APIs. Staging on Railway on every push to main that touches api/ or the engine; production from the production-api branch via the “Promote api to production” workflow.active
web/platform-web, the one Next.js App Router frontend for all three arms. Staging on Vercel on every push to main touching web/ or api/openapi.json; production from production-web via “Promote web to production”.active
assessment/The marking engine (packages/osce_assessment) and the assessment and assistant LiveKit workers. All worker changes go here. The api installs the engine straight from this folder (a Poetry path dependency), so an engine change and the api change that uses it land in one commit, and an engine change also redeploys the api's staging. Workers deploy to K3s after CI assessment passes on main; production from production-workers.active
b2b-api, b2c-apiThe legacy institution (FastAPI + Supabase) and consumer (Flask over Firestore) backends, in the old backend repository. Still serving the live site until the switch, and retiring; the source of the ported oracles. Do not start new work there.legacy
livekit/Frozen. Never edit or push. The retired worker project, outside this repository, with no traffic. It still contains the k8s, cluster and Ansible docs, which is why people open it and then edit the wrong thing. Retirement: livekit/README.md.do not touch

Services this backend depends on

PostgresEvery table, plus the procrastinate job queue in the same database — which is what lets a job be enqueued in the transaction that justifies it — and, since ADR 0019, the tutor's vector index too. Needs the vector extension: run pgvector/pgvector:pg16, not stock Postgres.required
RedisLiveKit Cloud slot counting only. Can be switched off with REDIS_DISABLED; the counters are shared with the legacy backends during coexistence, so the numbers must agree.optional
LiveKit CloudThe SFU is always Cloud. Only the agent workers are self-hosted. Cloud concurrency is metered and shared across every product, so past the cap sessions are served from our own workers rather than refused.required
K3s clusterRuns the self-hosted workers, which is what dodges the Cloud concurrency cap. Worker images are published to GHCR; staging deploys after CI assessment passes on main, production via the “Promote workers to production” workflow.required
OpenAI + AnthropicMarking. One default across every exam (gpt-6-luna at low effort, falling back to claude-sonnet-4-5) rather than b2c's and b2b's differing models producing results nobody can compare.required
StripeCheckout and webhooks. The webhook secret is per endpoint; without it deliveries are refused rather than trusted.required
ResendThe only mail provider, and an API key is its only configuration. Everything is sent through the outbound_messages outbox, never inline.required

Two things that will waste your first week

  • LiveKit Cloud showing “Updating”, or a worker showing offline, is usually normal. It is what a worker recycle looks like from the dashboard. Check the deploy logs, not the status page — this is a routine non-incident that reads exactly like an outage.
  • The job worker is load-bearing for live examinations, not only for marking. A circuit's transitions are jobs. A deployment with no worker running has examinations that start and never move, and the sweeper cannot help because it is itself a job. This is the main operational cost of ADR 0018 and is called out in app/worker/main.py.
  • Deploys are per folder, not per repository. A push to main deploys staging for whichever of api/, web/ and assessment/ changed; nothing reaches production until someone runs that app's promote workflow (production-api, production-web, production-workers). An engine change therefore runs CI api too and redeploys the api's staging.
Part six

Environment and secrets

Every setting is read once into one Settings object from the environment and, locally, .env. The design principle worth knowing before you read the table: secrets have no defaults outside local and test. A model validator refuses to start a staging or production process with any of the ten required values missing, which is how the “worker guard fails open” class of bug is prevented — a missing WORKER_SECRET cannot silently become an unauthenticated worker route.

Part seven

Six patterns that repeat

The decisions below are made once and then applied everywhere, which is what makes the rest of the schema predictable.

Versions freeze; references point at versions

station_versions, station_template_versions and rubric_versions are immutable once published. Everything recording what somebody was assessed on — attempts, slots, circuit stations, set entries, practice sessions — holds a station_version_id, never a station_id. Editing a station tomorrow cannot change yesterday's assessment.

Delete rules carry meaning

RESTRICT where a row is evidence: an attempt's slot, any station version something was sat against, a payment's user. CASCADE where the child is meaningless alone. SET NULL where the reference is attribution that survives the actor — published_by, signed_off_by, removed_by.

Idempotency is a column, not a convention

stripe_events.event_id, outbound_messages.idempotency_key, candidate_result_events.idempotency_key, transcript_messages.(attempt_id, message_id) and the partial unique on attempts.legacy_ref. A retry is a no-op rather than a second grant, a second email or a duplicated history.

Partial uniques carry the “only one live X” rules

One non-failed attempt per slot, one waiting queue entry per person per exam, one live entitlement lookup per user and exam. The rule lives in the index predicate, so no service can forget it and no race can beat it. ix_circuits_live is the same idea used for reading rather than for uniqueness: the exam-day board asks for running circuits constantly, and a running one is a vanishing fraction of the table.

Vocabularies live in the database where a typo would be silent

attempts.status and attempts.kind with its reference matching, entitlements.source, workflow_state with its signer and releaser rules, stations.owner_kind, rubrics.owner_kind, exams.owner_kind, and the three audience tables. Other status columns are enforced in the domain layer only.

JSON is used in five places, each on purpose

Org-authored shapes with no fixed columns (station_versions.content, rubric_versions.structure); the engine's own already-validated documents (attempts.definition, assessment_results.payload); a closed shape read as a unit (circuits.timing); shape-by-kind (media_items.content); and small metadata bags.

Part eight

What is not built yet

Taken from web/docs/BACKLOG.md and docs/EXPERIENCE-GAPS.md at commit 31a5e741, and checked against the routers. Items the code has since closed (the receipt document, SSO, SAML, SCIM and MFA, reindexing on publish, the partner report, the pinned engine, the e2e run) are gone from this list.

  • Consumer identity import needs a production export (M-1). The loader and verify step (scripts/migrate_legacy.py) are proven against a real database, dry run and idempotent re-run; the production Firestore export is still needed to size the run. Station sets, sittings and org data are not transformed.
  • The debrief clock and walk-through prompt are unproven live (V-1), and the debrief rarely reaches the differential (V-2). One staging debrief settles the first; the second is a prompt design question the bench has measured but not closed.
  • Enterprise readiness. Exposed credentials still to rotate (SEC-012, E-1); erasure and data download proven locally and on staging only (E-3); no data processing agreement template, subprocessor list with regions, or customer DPIA pack (E-6 to E-8). These are procurement blockers, not code.
  • Bulk revoke and resend have no web caller (B-36). /orgs/{slug}/memberships/bulk/revoke and /orgs/{slug}/trainees/bulk/* exist in the api and no screen reaches them.
  • Authoring is asymmetric between platform and organisation. Programmes exist only for an organisation; drafting a station from a prompt with no template is platform-only; a platform exam is retired rather than deleted. capabilities/authoring/api/scope.ts names them all.
  • The tutor's material index has two known blind spots. A templated station contributes nothing to it, because every block role a template can give is the patient's private material or the examiner's expected answers; and a section between two headings is never size-capped, a pinned quirk of the legacy chunker reproduced on purpose. Neither was re-verified at 31a5e741.
