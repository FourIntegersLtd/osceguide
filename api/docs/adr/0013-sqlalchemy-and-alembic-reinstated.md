# 0013. SQLAlchemy 2.0 and Alembic, reinstated

Date: 2026-09-16
Status: accepted; supersedes 0008 and restores the tooling of 0003

## Context
ADR 0003 chose SQLAlchemy and Alembic. ADR 0008 replaced them with plain SQL on psycopg 3,
citing two facts: the Supabase client speaks PostgREST, which cannot open a multi-statement
transaction or take a row lock, and the job queue needs a direct Postgres connection anyway.

Both facts are true and neither is an argument against SQLAlchemy. They are arguments against
`supabase-py`. SQLAlchemy 2.0 runs on psycopg 3, opens real transactions and takes
`SELECT … FOR UPDATE` locks, and the pre-0008 `app/core/db.py` already exposed `libpq_url()`
alongside `sqlalchemy_url()` precisely so procrastinate could keep its own direct connection.
The coexistence problem 0008 was avoiding had already been solved. So 0003 was superseded on a
premise that did not apply to it, and the genuine question — whether we want the abstraction —
was never argued.

Argued now, with a growing team as the deciding constraint, three things settle it:

- **Rows were untyped.** 0008's data layer sets `row_factory=dict_row`, so `dict[str, Any]`
  flows from repository into service and nothing checks that a key exists. That is the specific
  defect this project diagnosed in `b2b-api`, where the database row, the domain object and the
  API payload are one untyped dict. Mapped models give typed attributes end to end.
- **Nothing proved the schema and the code agreed.** Hand-written SQL files and hand-written
  queries can drift silently; the only defence was that every query happened to be covered by a
  repository test. Alembic autogenerate diffs the live schema against `Base.metadata` and makes
  drift a failing CI step instead of a discipline.
- **Roughly twenty slices of CRUD are coming.** Hand-writing and hand-mapping every select is a
  per-slice tax that compounds, and renaming a column becomes a grep across many SQL strings.

What plain SQL bought remains available: this codebase is reporting-heavy, and SQLAlchemy Core
`select()` expressions and `text()` are both first-class. Nothing forces an ORM query where a
join or an aggregate reads better as SQL.

## Decision
Postgres (Supabase-hosted when this was written; now Railway, see note below) through SQLAlchemy 2.0 async on the psycopg 3 driver. Slices declare
mapped models in `models.py`; schema changes are Alembic migrations, reviewed by hand after
autogenerate, applied by CI and on deploy. The request dependency yields one session inside one
transaction. procrastinate keeps its own direct psycopg connection via `libpq_url()`.

Reporting queries may be Core `select()` or `text()`; they stay inside `repository.py` either
way. Postgres functions and triggers we are porting wholesale (the candidate-result advisory
lock, idempotent release, and `FOR UPDATE SKIP LOCKED` outbox claim) remain hand-written SQL
inside migrations, which is what they already are.

## Consequences
- Repositories return typed mapped objects, so the untyped-dict failure mode is closed by the
  tool rather than by a guard we would have had to write.
- Migration drift becomes a CI failure; migrations stop being hand-authored files whose
  application order nobody records, which is the `b2b-api` failure this project set out to fix.
- Engineers must learn SQLAlchemy 2.0's declarative style and must review autogenerated
  migrations rather than trusting them — autogenerate misses constraint and index changes often
  enough that review is mandatory, not optional.
- The tenancy rule is unchanged: every org-scoped repository method still takes `org_id` first
  and is still guard-tested. An ORM makes cross-tenant leaks easier to write, not harder, so
  that guard matters more, not less.
- `app/core/migrations.py` and `supabase/migrations/` are removed; `alembic/` returns. Most of
  the reinstated layer is recoverable verbatim from commit `f563198`.
- Switching hosts away from Supabase still requires nothing but a new `DATABASE_URL`.

> **Note (2026-10-16).** That switch has happened: the database now runs on Railway
> (`platform-postgres` for staging, `platform-postgres-production`), built from
> `api/infra/postgres/Dockerfile` (Postgres 17 + pgvector). The decision above is unchanged.
